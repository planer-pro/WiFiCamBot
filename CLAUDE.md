# CLAUDE.md

**WiFiCamBot** — проект PlatformIO (Arduino): плата на модуле **ESP32-S3 N16R8** +
съёмный модуль камеры **OV2640** от классической ESP32-CAM. Камера стримит MJPEG
на веб-страницу по WiFi. Один исходник — `src/main.cpp`. Каталог проекта —
`WiFiCamBot` (переименован из `ESP32S3_Cam_LiveStream`).

## Команды

```bash
pio run -d .                  # сборка
pio run -d . -t upload        # прошивка (плата по USB, порт /dev/ttyACM0)
pio run -d . -e ota -t upload # прошивка по WiFi — ArduinoOTA (wificambot.local)
pio device monitor -d .       # монитор порта (115200)
```

## Железо и критичные решения

- **N16R8 = 16 МБ quad-flash + 8 МБ octal-PSRAM**: в `platformio.ini` обязательно
  `board_build.arduino.memory_type = qio_opi`, `board_upload.flash_size = 16MB`,
  `board_build.partitions = default_16MB.csv` и `-DBOARD_HAS_PSRAM`. Не убирать —
  иначе PSRAM не инициализируется и стрим деградирует.
- **lib_deps**: только `tzapu/WiFiManager` (настроечная точка доступа).
  Драйвер `esp32-camera` уже встроен в ядро arduino-esp32 2.0.17 (precompiled
  в SDK платформы espressif32) — из реестра его НЕ добавлять: библиотека там
  устаревшая и помечена `frameworks: espidf`.
- **Пины камеры** (блок «ПИНЫ КАМЕРЫ» в начале `src/main.cpp`) — распиновка
  Freenove ESP32-S3-WROOM CAM по умолчанию. Точная модель платы пользователя
  неизвестна: если камера не инициализируется — менять нужно только этот блок
  (таблица и ссылки в README).
- **RGB-светодиод** — WS2812 на GPIO 48 (подтверждено на плате пользователя
  тестом с кнопками). Отправка — собственный драйвер `wsSendColor()` через RMT
  (`driver/rmt.h`, канал 0, тик 50 нс). Штатный `neopixelWrite()` ядра 2.0.17
  этот светодиод НЕ зажигает (пин при этом верный) — на него не возвращаться.
- **I2S не занимать** — планируется I2S-устройство (микрофон/усилитель).
  Периферия I2S0/I2S1 прошивкой не используется и не должна: камера на
  ESP32-S3 идёт через LCD_CAM (не через I2S, как на классическом ESP32),
  светодиод — RMT, моторы — LEDC. Под I2S оставлены свободными GPIO 21,
  38–42, 47 (на S3 I2S назначается на любые GPIO через матрицу сигналов) —
  новые функции на эти пины не сажать.
- **Отладки (Serial/LOG) в коде нет** — удалена по просьбе пользователя: на этой
  плате вывод прошивки в монитор не доходит (стартовый ROM-лог приходит), что
  проверено минимальным скетчем и прямой записью в FIFO USB — дело не в коде
  проекта. Возвращать не предлагать.

## Карта выводов (GPIO)

| Выводы | Статус |
|---|---|
| 1, 2, 3, 14 | моторы MX1508 (3 — strapping-пин, но как выход после загрузки безопасен) |
| 4-18, кроме 14 | камера OV2640 (точный список — блок «ПИНЫ КАМЕРЫ») |
| 48 | WS2812 RGB-светодиод |
| 21, 38-42, 47 | резерв под I2S (рекомендация: DATA=21, BCLK=41, WS=42) — не занимать |
| 43, 44 | свободны (UART0 не используется; плата на нативном USB 19/20) |
| 0, 45, 46 | strapping (0 — ещё и кнопка BOOT) — не использовать |
| 19, 20 | USB-разъём (прошивка по проводу, питание) — не использовать |
| 26-32 | шина SPI-flash внутри модуля — не использовать |
| 33-37 | шина octal-PSRAM внутри модуля — не использовать |
| 22-25 | на ESP32-S3 физически не существуют |

SD-карта и проводной последовательный порт не планируются — пины под них не
резервируются.

## Устройство кода

- **WiFi — через WiFiManager** (`connectWiFi()` в `setup()`): подключение к
  сети, сохранённой в NVS; не удалось за 15 с — `wm.autoConnect(WIFI_AP_NAME)`
  поднимает настроечную точку доступа (имя — `WIFI_AP_NAME` в
  `wifi_secrets.h`, у нас `wificambot-setup`) с captive-порталом выбора сети;
  выбранное сохраняется в NVS, портал без действий 2 мин — перезапуск.
  Учётные данные сети в `wifi_secrets.h` НЕ задаются (убраны по просьбе
  пользователя) — там только имя AP и опциональный пароль OTA.
  В `loop()` связь контролируется: короткие пропадания лечит автореконнект,
  пропажа дольше 20 с — портал поднимается прямо из `loop()`
  (`startConfigPortal`, без перезагрузки): наши httpd-серверы на время
  портала останавливаются (`stopWebServer()` — порт 80 нужен порталу
  WiFiManager), после выбора сети поднимаются заново (`startWebServer()`);
  таймаут портала 2 мин — `ESP.restart()`. Таймауты — константы `WIFI_*`
  возле `connectWiFi()`, общий конфиг обоих порталов — `wmConfigure()`.
  После УСПЕШНОГО портала (и в `connectWiFi()`, и в `loop()`) вызывается
  `wmClosePortal()`: библиотека после успеха портал сама не сворачивает —
  её WebServer продолжал бы держать порт 80 (в коде WiFiManager 2.0.17 это
  @todo), поэтому сворачиваем вручную (`setConfigPortalBlocking(false)` +
  `stopConfigPortal()` — в блокирующем режиме один `stopConfigPortal` лишь
  ставит флаг и ничего не освобождает).
  Проверено на железе (имитация обрыва): AP через ~20 с, портал 2 мин,
  затем перезапуск и самостоятельное возвращение в сеть.
  Пока портал поднят, светодиод МИГАЕТ синим (переключение каждые 500 мс,
  `s_portalBlink` + задача `portalBlinkTask` в отдельной задаче FreeRTOS — оба
  подъёма портала блокирующие, `loop()` в это время стоит, мигать больше некому;
  флаг ставит `setAPCallback` в `wmConfigure()`, снимает `portalBlinkStop()`
  после сворачивания портала). После подключения возвращается сохранённое
  состояние света (`applyLight()`).
- Сервер — `esp_http_server` из ESP-IDF, **два экземпляра**: порт 80 — `/`,
  `/set?quality=|rot=|light=|color=|motor=|mix=|ctrl=|speed=|tspeed=|accel=|taccel=|start=`
  и `GET /status` (все текущие настройки одним JSON — для Android-клиента:
  обе пары мощностей из NVS напрямую, `status_handler` рядом с `set_handler`),
  порт 81 — только `/stream`. Поток httpd у каждого экземпляра один, а
  `stream_handler` — бесконечный цикл: держать
  стрим на одном сервере с `/set` нельзя (пока открыт стрим, остальные запросы
  этого сервера не обслуживаются — из-за этого «не работали» кнопка света и
  качество; проверено на железе). Страница строит абсолютный URL стрима
  `http://<host>:81/stream` в JS — относительной ссылки на другой порт нет.
  Стрим можно открыть и напрямую (VLC и т.п.): `http://wificambot.local:81/stream`.
- Качество (разрешение + jpeg_quality) — таблица пресетов `QUALITY_PRESETS`,
  применяется на лету `applyQuality()` без переинициализации камеры. Пресеты
  только 4:3 — из-за CSS-поворота страницы.
- Свет — таблица `LIGHT_COLORS` + `applyLight()` → `wsSendColor()` (RMT);
  состояние `g_lightOn`/`g_lightColor`, меняется через `/set?light=|color=`.
- **Моторы гусениц** — драйвер MX1508, танковая схема: канал A (IN1/IN2) —
  левая гусеница, B (IN3/IN4) — правая; ШИМ на один вход канала, второй в 0 =
  направление. Пины — блок «МОТОРЫ ГУСЕНИЦ (MX1508)» в `src/main.cpp`
  (по умолчанию GPIO 1, 2, 3, 14 — подобрать под свою проводку). Команды
  `/set?motor=f|b|l|r|s` (повороты — разворот на месте), мощность
  `/set?speed=N%` (вперёд/назад) и `/set?tspeed=N%` (повороты) — мощность
  хода и поворотов настраивается раздельно. Разгон (плавный набор мощности
  при старте): `/set?accel=` / `/set?taccel=` в мс из `MOTOR_ACCEL_STEPS`
  ({0, 200, 500, 1000, 2000}, 0 = отключено), тоже раздельно для хода и
  поворотов, умолчание 500 мс; N мс — время набора до УСТАНОВЛЕННОЙ мощности,
  а не до 100 % (шаг `motorsTick` пропорционален диапазону [точка
  страгивания … цель], не полной шкале). **Точка страгивания** `/set?start=N%` ШИМ
  (0..90, умолчание 0 = как раньше): моторы трогаются не с нуля, поэтому
  шкала сдвигается — 1..100 % мощности ложатся на диапазон [точка … полная]
  (`dutyFromPct()`), 0 % остаётся честным нулём; действует на кнопки,
  клавиши, трекпад и геймпад одинаково (свойство моторов, не вида
  управления);
  разгон стартует сразу с точки (`dutyLo()`), не тратя время на мёртвую
  зону. Реализация: `applyMotors()` считает целевую
  скважность каналов (`g_chTarget`), рост к цели делает `motorsTick()` из
  `loop()` (цикл 20 мс ради мелких шагов), а ЛЮБОЕ снижение мощности и стоп —
  мгновенно (безопасность: торможение не зависит от настроек разгона).
  Пульт на странице: кнопки-крестовина
  (удерживать; ▼ S в центре, отдельной кнопки «стоп» нет — стоп даёт
  отпускание) и клавиши —
  стрелки и WASD; клавиша обрабатывается по `ev.code`, чтобы работало в
  русской раскладке. Пока направление удержано, страница повторяет команду
  каждые 500 мс; плата сама даёт стоп, если команд нет 1.5 с (`loop()`,
  страховка от обрыва WiFi/закрытия вкладки — при обрыве робот не уедет).
  Отпускание — стоп дублируется ещё дважды с интервалом 400 мс
  (`stopRepeat()` в JS, все виды управления): при WiFi-провале застрявшие
  в очереди команды движения догоняют плату ПОСЛЕ стопа и сбрасывают
  таймаут — робот «ехал после отпускания» ещё секунды; повторный стоп
  приедет за очередью. Новое движение отменяет повторы.
- Страница `INDEX_HTML`: подстановка текущих значений вместо меток
  `@Q@`/`@L@`/`@C@`/`@S@`/`@T@`/`@R@`/`@A@`/`@B@`/`@P@`/`@K@` (`@A@`/`@B@` —
  разгоны хода/поворотов, `@P@` — вид управления, `@K@` — точка страгивания)
  в `index_handler`
  (chunked-ответ, с заголовком
  `Cache-Control: no-cache` — чтобы после перепрошивок браузер не держал
  старый JS). Список цветов в HTML обязан совпадать с `LIGHT_COLORS`
  по индексам, значения разгона — с `MOTOR_ACCEL_STEPS`.
- **Настройки хранятся в NVS** (Preferences, namespace `cam`): качество,
  поворот кадра, свет вкл/выкл + цвет, мощности (пара кнопочного вида и
  общая пара аналоговых), оба разгона, точка страгивания, вид
  управления. Читаются
  `settingsLoad()` в начале `setup()`, пишутся при каждом изменении через
  `/set`. Направление движения
  (`motor=`/`mix=`) не сохраняется. Проверено на железе: значения переживают
  перезагрузку питания/перепрошивку (NVS при OTA не стирается) и отдаются
  странице метками при открытии браузера.
- **Вид управления** — список «Управление» в группе «Моторы»: кнопки
  (крестовина), трекпад или геймпад (`/set?ctrl=0|1|2`, NVS-ключ `ctrl`,
  метка `@P@`).
  Трекпад — круглый аналог-джойстик под видео: палец задаёт направление И
  мощность — отклонение от центра даёт процент от настроенного предела
  (край круга = выбранная в списке мощность; вертикаль — ход, горизонталь —
  поворот, в центре мёртвая зона, отпускание — стоп). Он шлёт
  `/set?mix=L,R` — раздельную мощность гусениц −100..100% (знак =
  направление, `0,0` = стоп), уже умноженную на пределы: прошивка смешивает
  ход и поворот в каналы (`motorMix()` → команда `'m'` в `applyMotors()`)
  мгновенно, без разгона. **Геймпад** (`ctrl=2`) — Bluetooth-геймпад,
  подключённый к САМОМУ устройству с браузером (телефону/компьютеру),
  робот про него не знает: страница опрашивает его через Gamepad API
  (`gpadPoll()` каждые 50 мс), левый стик задаёт тот же вектор, что палец
  на трекпаде, — те же `/set?mix=` (расчёт общий: `mixFromVec()`); круг
  трекпада остаётся на экране индикатором (ручка ходит за стиком, класс
  `ro` — касания не ловит), под ним строка состояния
  (`gstat`: найден / «нажмите любую кнопку» — браузер отдаёт геймпад
  списком только после нажатия кнопки на нём). Мёртвая зона 0.15 с
  растяжкой шкалы на весь ход стика; при удержании микс повторяется
  каждые 500 мс (страховка от таймаута команд), blur окна — стоп, как у
  клавиш. ВАЖНО: Chrome/Firefox дают Gamepad API только HTTPS-страницам —
  по обычному HTTP (наш случай) геймпад в браузере не виден. В Chrome
  обход — флаг `chrome://flags/#unsafely-treat-insecure-origin-as-secure`
  с адресом робота + перезапуск; в Firefox обхода НЕТ (у пользователя
  именно Firefox): либо Chromium с этим флагом, либо проброс портов на
  localhost — его браузеры считают безопасным контекстом (готовый `tunnel.sh` в корне репозитория: пробросы
  127.0.0.1:8080→робот:80 и 127.0.0.1:81→робот:81, открывает
  http://localhost:8080, стрим страница сама берёт с localhost:81;
  проверен на живом роботе, останов — Ctrl+C. Локальный порт 81
  привилегированный: на машине разработчика socat уже имеет setcap
  cap_net_bind_service (работает без sudo), на новой машине дать:
  `sudo setcap cap_net_bind_service=+ep "$(readlink -f "$(command -v socat)")"). Страница сама подсказывает
  это в строке состояния, если `!window.isSecureContext`.
  Мощности действуют во всех видах управления
  (поля всегда активны, менять можно на лету): у кнопок своя пара, у
  трекпада с геймпадом — общая; хранятся раздельно (NVS: кнопки —
  `speed`/`tspeed`, аналоговые виды — `pspeed`/`ptspeed`),
  `/set?speed=`/`/set?tspeed=` пишутся в ключи
  активного вида, а `/set?ctrl=` в ответе отдаёт пару выбранного вида
  («ход,поворот») — страница подставляет её в поля (`loadPowers()`).
  Разгоны — настройка
  кнопочного режима: в аналоговых видах их строка гасится, поля неактивны
  и показывают «отключено», и в прошивке так же — любое движение
  мгновенное и для стика, и для клавиш (`g_chAccelMs = 0` при
  `g_ctrlMode != 0`); сохранённые значения страница возвращает в режиме
  кнопок (в NVS не пишет).
- **Поворот кадра на странице** — список «Поворот кадра» (0/90/180/270°,
  умолчание 90: камера на платформе стоит повёрнутой). `setRotation()` в JS
  меняет аспект сцены (3:4 ↔ 4:3), ширину картинки и `rotate()` — кадр
  заполняет сцену целиком, без чёрных полей; рамка крутится вместе с ним.
  Хранится на плате (`/set?rot=N`, NVS-ключ `rot`) и подставляется меткой
  `@R@`. Сенсор сам кадр не крутит — только CSS.
- Камера: JPEG, 2 буфера в PSRAM, `CAMERA_GRAB_LATEST`.
- **OTA-прошивка по WiFi** — ArduinoOTA (встроен в ядро, UDP-порт 3232): init в
  `setup()` после `startWebServer()`, `ArduinoOTA.handle()` в `loop()`. mDNS у
  библиотеки отключён (`setMdnsEnabled(false)`): её `begin()` поднял бы второй
  mDNS и сломал `wificambot.local` — служба `_arduino._tcp` добавляется вручную
  через `MDNS.enableArduino(3232)` в уже работающий mDNS. Прогресс обновления
  дублируется RGB-светодиодом (`onStart`/`onProgress`/`onEnd`/`onError` —
  Serial-отладки на плате нет). Пароль необязателен: `OTA_PASSWORD` в
  `wifi_secrets.h` + `upload_flags = --auth=…` в env `ota`. Прошивание — env
  `ota` в `platformio.ini` (`upload_protocol = espota`); `default_envs =
  esp32s3_cam`, чтобы `pio run -t upload` без `-e` не лез по сети. Разделы
  `ota_0`/`ota_1` уже есть в `default_16MB.csv` — таблицу разделов не менять.
  Проверено на железе: OTA при открытом стриме работает (кадры замирают на
  время записи, потом всё продолжает).

## Android-клиент (android-app/)

Flutter-приложение — пульт робота (сборка и установка — `android-app/README.md`;
прошивке нужен `GET /status`). Устройство:

- **Один экран без скролла** (`screens/main_screen.dart`): видео сверху,
  панель управления фиксированной высоты (портрет) или ширины (ландшафт);
  в портрете высота панели ОДИНАКОВА во всех видах управления (крестовина,
  трекпад, геймпад — как у крестовины, 2 ряда) — окно видео не меняет размер
  при смене вида (`_controlPanel`, размер трекпада/индикатора от неё же).
  В верхней панели — быстрые органы: выпадающее меню вида управления
  (`_changeCtrl` — порт `_changeCtrl` настроек: оптимистично + откат,
  ответ `/set?ctrl=` с парой мощностей кладётся в свою пару) и кнопка
  света вкл/выкл (`_toggleLight`, цвет не трогает). Индикатор связи
  обёрнут в `ListenableBuilder` на стрим — сам обновляется при смене
  состояния (иначе «Подключение…» висело до первого нажатия кнопки).
  Чтение `/status` — отдельный клиент `_statusRobot` с таймаутом 8 с
  (облако Keenetic отвечает до 7 с; командам движения остаётся 3 с);
  если робот не ответил, опрос повторяется каждые 3 с сам (`_statusRetry`)
  — после переключения профиля/перезагрузки робота индикатор доезжает
  до истины без нажатий. В `RobotClient` таймаутом ограничено и ЧТЕНИЕ
  ТЕЛА ответа (`drain`/`join`), не только соединение: зависший на середине
  ответ (обрыв релея облака, полумёртвый keep-alive) иначе навсегда
  занимал конвейер команд — моторы и свет умирали разом при живом стриме.
  Этого оказалось МАЛО (подтверждено на железе 2026-08-29: робот чуть
  проезжал и замолкал навсегда при ЗЕЛЁНОМ индикаторе — `/status`-клиент
  жив, командный стоит): при `maxConnectionsPerHost=1` незакрытый таймаутом
  `getUrl` ждал единственный слот пула вечно. Теперь ВСЕ шаги запроса под
  таймаутом (включая `getUrl` — ожидание слота), при сбое в путях команд
  клиент пересоздаётся с `close(force:true)` (`_recycle` с identical-защитой
  от двойного пересоздания) — зависший сокет рвётся, управление оживает
  само за ~3–4 с; на весь `_doSet` в конвейере поясной таймаут. Прогрев
  `warmUp` и `/status` при сбое клиент НЕ пересоздают (через облако те
  часто не укладываются в таймаут — churn рвал бы прогретое соединение),
  их застрявший слот вылечит любая неудачная команда.
- **Вид управления** берётся с робота (`/status`): 0 — кнопки-крестовина
  (`widgets/dpad_widget.dart`: сетка 3×2 как в браузере — ▲ над центром,
  ◀▼▶ одним рядом; корневой AspectRatio + Expanded-клетки, НЕ голые
  AspectRatio в строке — строка даёт бесконечную высоту, клетка раздувалась
  на всю ширину и кнопки улетали за экран), 1 — экранный трекпад
  (`widgets/joystick_widget.dart`, математика трекпада), 2 — Bluetooth-геймпад
  к телефону: `MainActivity.kt` читает ось левого стика через
  `dispatchGenericMotionEvent` (EventChannel `wificambot/gamepad`, троттлинг
  50 мс; разрешений BT не нужно — это устройство ввода), круг на экране —
  индикатор. Событие, попавшее в окно троттлинга, НЕ выбрасывается, а
  откладывается до его конца (коалесинг): иначе терялось ПОСЛЕДНЕЕ событие —
  возврат стика в ноль при отпускании, и индикатор замирал отклонённым
  (моторы доезжали до сторожевого таймера платы).
- **Логика движения** (`core/motor_controller.dart`) — порт веб-версии:
  повтор активной команды каждые 500 мс, стоп с двумя дублями по 400 мс,
  новое движение дубли отменяет; уход в фон/в настройки — немедленный стоп.
  Смешивание ход+поворот в мощности гусениц — `core/mix_math.dart`
  (1:1 с `mixFromVec` страницы, дедзоны 0.12/0.15).
- **MJPEG** (`core/mjpeg_stream.dart`): свой HttpClient + разбор multipart
  (boundary из Content-Type, кадр по Content-Length), декод с
  `targetWidth` под размер виджета, очередь декода 1, реконнект через 1 с.
  Смена качества/адреса — `restart()` (рвёт соединение).
- **Настройки** (`screens/settings_screen.dart`): «Подключение» — **два
  профиля с раздельными адресами** («Подключение локальное» — дома;
  «Подключение интернет» — облако/туннель), каждый со своими полями
  (адрес робота, порт стрима, полный URL стрима — необязательный override
  для облака Keenetic) и своей кнопкой «Проверить связь»; радио-плитки
  (общий `RadioGroup`) выбирают активный профиль. Модель —
  `core/app_settings.dart` (`ConnProfile` ×2 + `ConnKind` в `AppSettings`,
  хранится в SharedPreferences; при первом запуске после обновления старый
  одиночный адрес мигрирует в оба профиля). «Робот»
  (все настройки робота, чтение
  `/status`, запись `/set` с оптимистичным UI и откатом), «Приложение»
  (язык интерфейса, смена пароля). Экран возвращает `(AppSettings, RobotSettings?)` — главный
  экран применяет адрес и перезапускает стрим.
  На главном экране возле индикатора связи — быстрое меню «Локальное /
  Интернет» (`_switchConn` в `main_screen.dart`: стоп моторов, смена
  профиля, сохранение, перезапуск стрима).
- **Пароль входа** (дефолт `1234`): хэш sha256+соль в SharedPreferences
  (`core/app_settings.dart`), экран блокировки `screens/lock_screen.dart`.
  Пароль ТОЛЬКО ЦИФРОВОЙ и вводится с собственного крупного пада
  (1–9/⌫/✓, точки вместо символов, тактильный отклик) — системная
  клавиатура не вызывается вовсе (TextField не создаётся). Поля смены
  пароля в настройках ограничены `digitsOnly` и длиной 12: нецифровой
  пароль на паде не ввести (установивший его ранее лишится входа —
  лечится сбросом данных приложения).
- **Язык интерфейса** — русский/English, выпадающий список в настройках
  («Приложение»), применяется сразу и хранится в SharedPreferences
  (ключ `locale`, `SettingsStore.locale/saveLocale`). Механизм — лёгкий
  свой, без gen_l10n: таблицы строк `Strings` (_ru/_en) в `core/l10n.dart`,
  доставка — InheritedWidget `L10n` НАД MaterialApp (строки берутся
  `L10n.of(context).…`), смена — глобальный `localeNotifier` (главный
  виджет его слушает и перестраивает дерево). Пункты списка — на самих
  языках («Русский»/«English»), не переводятся. Текстовые подписи робота
  (качество, цвета, виды управления, разгоны) переехали из
  `models/robot_settings.dart` в `Strings` — там ИНДЕКСЫ общие с
  таблицами прошивки, а строки локализованы; `colorSwatches`/`accelSteps`/
  `rotSteps` (значения, не текст) остались в `robot_settings.dart`.
- Манифест: `INTERNET` + `usesCleartextTraffic` (робот по http), метка
  «WiFiCamBot». Пакет `local.wificambot.wificambot`.

### Доступ извне локальной сети (роутер Keenetic, 192.168.1.1)

У провайдера **серый IP (CGNAT)**, IPv6 LAN не раздаётся — напрямую роутер
из интернета недостучаться. Используется **облако Keenetic (KeenDNS)**:
домен `myhome3.netcraze.link`, режим доступа «через облако». В облаке
опубликованы два сервиса (RCI `ip.http.proxy`, поддомен = имя записи):

- `https://robot.myhome3.netcraze.link` → робот `192.168.1.137:80` (сайт+`/set`);
- `https://stream.myhome3.netcraze.link` → робот `192.168.1.137:81` (`/stream`).

В приложении для работы извне: адрес робота
`https://robot.myhome3.netcraze.link`, полный URL стрима
`https://stream.myhome3.netcraze.link`; дома — обычный
`http://192.168.1.137`. Трафик идёт через релеи Keenetic (только HTTPS,
пропускная способность ограничена; проверено: MJPEG течёт).

WireGuard-сервер на роутере пробовали (IPv6 WAN у провайдера есть), но
туннель с мобильных не собирается — у операторов нет IPv6 / режется входящий
UDP; настройка и компоненты `wireguard`/`wireguard-server` удалены по просьбе
пользователя. При появлении белого IP — альтернатива без облака, поднимается
заново. API роутера:
`GET /auth` (401 + заголовки `X-NDM-Challenge`/`X-NDM-Realm`) →
`sha256(challenge + md5(login:realm:пароль))` → `POST /auth
{"login","password":hash}` (куки, сессия 5 мин) → REST `/rci/...`
(установка/удаление компонентов — `components/install|remove|commit`,
публикации — `ip/http/proxy`). CLI — по telnet 192.168.1.1 (порт 23),
пиры WG адресуются ключом: `wireguard peer <base64-ключ>`.

## Подводные камни (проверено на этой версии ядра)

- Имена enum — `CAMERA_FB_IN_PSRAM` / `CAMERA_FB_IN_DRAM` (не `CAMERA_PF_*`).
- `httpd_query_key_value` НЕ декодирует `%XX`: клиенты, кодирующие запятую
  в `/set?mix=L,R` как `%2C`, молча игнорировались (джойстик Android-пульта
  «не ехал»). Значение mix проходит через `urlDecode()`; клиенты обязаны
  слать запятую буквальной (Dart `queryParameters` кодирует — собирать
  query вручную).
- `STREAM_BOUNDARY` — это `#define`-макрос, а не `const char[]`: он
  склеивается со строковыми литералами при компиляции.
- В хэндлерах после `esp_camera_fb_return(fb)` поля `fb` читать нельзя —
  сохранять нужное (`len`) до возврата буфера.
- Ошибка `esp_camera_init` `0x20004`/`0x105` — почти всегда чужая распиновка.
- Один поток httpd на экземпляр сервера: незавершающийся хэндлер (`/stream`)
  блокирует ВСЕ прочие запросы этого сервера, а не только своё соединение —
  поэтому стрим вынесен на отдельный порт 81 (см. «Устройство кода»).
- Буферы кадра выделяются под `frame_size` на момент `esp_camera_init`:
  камера инициализируется под максимальный пресет (UXGA), а стартовый уровень
  применяется сразу после (`applyQuality(QUALITY_DEFAULT)` в `initCamera`).
  Без этого переключение вверх по разрешению (уровень 4) подвешивает стрим —
  проверено на железе.
- Открытие `/dev/ttyACM0` дёргает RTS и сбрасывает плату, а после такого
  сброса HTTP-сервер может молчать (пинг и mDNS при этом отвечают). Лечится
  чистым сбросом: `python3 ~/.platformio/packages/tool-esptoolpy/esptool.py
  --port /dev/ttyACM0 --chip esp32s3 --after hard_reset chip_id` и ожиданием
  ~30 с. Порт без нужды не открывать.
- OTA и USB-прошивку можно чередовать без «старого слота»: после OTA плата
  грузится из `ota_1`, но USB-заливка pio пишет и `boot_app0.bin` (otadata),
  возвращая загрузку на `ota_0`.
- **LEDC-канал 0 и таймер 0 заняты камерой** (XCLK 20 МГц). Моторы MX1508 —
  каналы 1–4 на таймере 1 (ШИМ 20 кГц, 10 бит). Arduino-функции `ledcSetup`/
  `analogWrite` не использовать: `ledcSetup(1, …)` в ядре 2.x перенастроил бы
  таймер 0 и сломал бы XCLK камеры.
